# OpenRig 0.6.4 — web UI off by default, browser checks, and repairs

> Backfilled release note, written 2026-10-24 from the `0.6.4` section of
> [`CHANGELOG.md`](../../CHANGELOG.md). The changelog section is unusually complete
> and is the authority; this page condenses it without adding claims.

0.6.4 is the code tested and published as the 0.6.4-rc.1 release candidate, now the
normal release. It was cut from main at `afde814f`, then changed only by the bounded
repairs below, the web UI default, and browser access with its docs page.

## Two changes you might notice

- **The web UI is off by default.** The daemon no longer serves the web UI's pages
  or its terminal connection unless you turn it on with
  `rig config set ui.enabled true` and then stop and start the daemon. While it is
  off, opening the page shows those steps and `rig ui open` prints them. The web UI
  is in maintenance mode; the CLI and TUI are the supported surfaces.
- **The daemon checks the request's address and web page origin.** Nothing changes
  for the CLI, TUI, agents, queue, Slack, or hosts reaching this machine by IP,
  hostname or Tailscale name. If you reach the daemon by a custom DNS name, an
  `/etc/hosts` alias or a reverse-proxy domain, add it to
  `OPENRIG_ALLOWED_HOSTS`. If a local app on another port calls the daemon from a
  browser, add its origin to `OPENRIG_ALLOWED_ORIGINS`. Each refusal says which
  setting to add; both need a daemon restart.

The `0.6.4` section records no database migration for this release.

## Repairs made after the candidate was cut

- Bundles keep binary files intact (`rig bundle create` no longer re-encodes them).
- A daemon started with `rig daemon start --port` is the one other local commands
  talk to.
- A single-seat rig can be relaunched fresh after the old seat's stop ended the tmux
  server.
- A managed Claude launch with an explicit permission mode gives `claude --help`
  five seconds instead of one.
- Fresh launches and restores use the running version's built-in startup files after
  an upgrade removes the old install.
- After a full down and up, a resumed Claude seat in auto mode accepts ordinary
  messages again once OpenRig confirms the same process in its pane; an
  unconfirmable resume asks for attention instead of starting fresh.
- A natively installed Claude behind the managed shell wrapper is recognized. When
  the runtime cannot be observed, ordinary delivery proceeds with a warning; a
  plainly idle shell or wrong recipient is still refused.
- Restoring an older Claude seat keeps an uncertain launch and asks for attention
  instead of closing the new session.
- `rig proof add --replace` swaps in a new file, so a symlinked or hard-linked
  artifact no longer overwrites the other path.
- A Slack message from a registered person is stored with its complete text;
  previously anything past 1,800 characters was lost. A retry storage error is
  logged instead of escaping.

## Verification performed (as recorded then)

- Required checks covered build and packaging, types, repository checks, package
  test suites and an installed-package scenario.
- Scripted checks ran installed candidate builds. Three known failures remained:
  two plugin usage-reporting cases (fixed on main for the next release) and
  `rig proof add --file` dropping a leading byte-order mark.
- A fresh first-time install ran Claude-only, Codex-only and mixed teams through
  useful work, a warm resume and a graceful reboot.
- Real Claude Code agents on a test server took and answered a message after a full
  down and up, carried on with their own queue work, and kept the conversation
  through a daemon restart.
- Final-package Slack checks used synthetic connections on Linux; they were not a
  live Slack test or a whole-daemon fault trial.

This backfill did not re-run those checks.

## Known limits at the time

- A restore could report a problem with a seat that worked; `rig restore-check`
  could also report a failure for that rig.
- Codex under its default workspace-write sandbox could not reach the local daemon
  in the test-server run, blocking its queue work.
- After a reboot the daemon does not come back on its own; start it, then
  `rig up <name>`.
- Stopping the daemon can report a timeout while closing connections.
- Setup's optional cmux step can report an error.
- Browser access is not complete browser isolation; keep the daemon on loopback or
  your tailnet.
- Windows was not tested.
